## Gaps, Overlaps, And Duplications

- Docs mention end-to-end discovery, RFP ingestion, compliance, e-signature, payments, external partner workspaces, global source coverage, mobile/offline, and enterprise integrations; code support ranges from substantial partial implementation to roadmap-only.
- Code capabilities absent or underrepresented in high-level docs include detailed CRM, pricing, evidence, graphics, presentations, import rollback, schema parity, agent memory, and many frontend domain actions.
- Duplicate concepts appear in requirements tables/history (`requirements` versus `rfpRequirements` is explicitly called out in docs), compliance matrix naming (`complianceMatrix` versus `complianceMatrices` patterns), workflow/process constructs across frontend schemas and Python workflow engine, and intelligence/evidence schemas repeated in consolidated and domain files.
- UI actions without complete backend support include some analytics panels, presentation analysis/export, external partner collaboration, some diagram/graphics generation paths, and final submission/e-signature flows.
- Backend routes without full UI/support include some FastAPI RFP/discovery endpoints and webhook-style capabilities.
- Workflows without task projection include gates, compliance gaps, comments, evidence findings, DLP findings, parser failures, import conflicts, and integration failures.
- Tasks exist with rich status fields, but universal state semantics for pause, reopen, cancel reason, waiver, and compensation are not normalized.
- Notifications exist across packages/actions, but many are logs/webhooks/placeholders without central actionable notification records.
- Audit evidence is present in concept and some modules, but many domain mutations need actor/reason/before-after/evidence/correlation IDs.
- Domain statuses should be normalized into workflow states for parse status, requirement compliance status, review status, evidence status, pricing approval status, theme injection status, import status, scraper health, notification delivery, and render/submission status.
- Failure handling is distributed. A global exception queue for failed jobs, stalled workflows, and integration errors is missing or implied.
- Reversal/reopen/correction paths are not consistently modeled despite terminal states and high-risk proposal workflows.

## Definition Of Done For A Workflow-Backed JTBD

- Canonical subject exists.
- States and terminal states are explicit.
- Legal transitions are explicit.
- Permissions/authority are enforced server-side.
- Required data, documents, and evidence are modeled.
- Waivers and reason codes are modeled.
- SLA, pause, breach, and escalation behavior exists.
- Tasks project into the user's work queue.
- Notifications are actionable.
- Audit trail records actor, reason, before/after, evidence, and timestamp.
- UI shows current state, owner, next action, blockers, deadline, and history.
- Tests cover happy path, blocked path, authority failure, SLA breach, and reversal/reopen if applicable.
